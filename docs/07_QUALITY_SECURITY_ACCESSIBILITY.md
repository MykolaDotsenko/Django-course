# Quality, Security and Accessibility

## 1. Quality target

The repository should demonstrate a production-minded engineering baseline without turning a portfolio application into ceremony.

## 2. Python quality

Target tools:

- Ruff for linting and formatting;
- pytest;
- pytest-django;
- coverage;
- mypy or another justified type-checking setup for application boundaries;
- pre-commit;
- dependency vulnerability audit.

Remove duplicated formatters/linters once Ruff covers the required rules.

## 3. Test pyramid

### Domain unit tests
Fast and exhaustive for:

- Decimal conversion;
- rounding;
- input limits;
- provider normalization;
- country/currency validity;
- stale semantics;
- price-context classification.

### Django tests
Cover:

- models and constraints;
- forms;
- views;
- permissions;
- cache behaviour;
- HTMX full/partial response distinction.

### Provider contract tests
Use recorded/fixture payloads.

Do not make normal test runs depend on live third-party APIs.

### Browser E2E
Playwright for:

- first conversion;
- swap;
- invalid input;
- provider failure/stale recovery;
- mobile viewport;
- keyboard flow;
- favourites/history when shipped.

### Accessibility
Automated axe checks plus manual keyboard and screen-reader-oriented review.

Automated checks do not prove full WCAG conformance.

## 4. CI gates

Every pull request should eventually run:

```text
format check
lint
type check
unit/integration tests
migration check
coverage threshold
dependency audit
Django deployment checks
frontend CSS build
Playwright smoke/accessibility
```

Run expensive browser jobs separately from fast unit jobs.

## 5. Security baseline

### Settings
- secret key from environment;
- `DEBUG=False` in production;
- explicit allowed hosts;
- secure cookie settings in production;
- HSTS after HTTPS deployment is verified;
- trusted proxy/header configuration documented.

### Django protection
Keep built-in protections enabled:

- CSRF;
- auto-escaping;
- ORM parameterization;
- clickjacking middleware;
- password validation.

### HTMX
HTMX increases the expressive power of HTML, so injected markup is more dangerous.

Rules:

- never render unsanitized user HTML;
- keep Django escaping on;
- validate all mutation requests server-side;
- enforce CSRF on unsafe methods;
- prefer declarative HTMX attributes generated by trusted templates.

### External providers
- strict timeouts;
- bounded retries;
- response validation;
- no secrets in logs;
- no provider error payload blindly rendered to users.

## 6. Authorization

Every user-owned object must enforce ownership server-side.

Never rely on hiding buttons.

Test:

- direct URL access;
- update/delete of another user's record;
- object enumeration;
- API ownership.

## 7. Privacy

Anonymous conversion should not require tracking.

If history becomes durable:

- make persistence behaviour explicit;
- provide deletion;
- minimize stored personal data;
- define retention;
- avoid storing unnecessary IP/user-agent details.

## 8. Accessibility baseline

Target **WCAG 2.2 AA**.

Specific requirements:

- semantic landmarks;
- labelled inputs;
- logical heading order;
- visible focus;
- keyboard completion of all P0 flows;
- 4.5:1 text contrast where applicable;
- no colour-only state;
- adequate target sizes;
- error identification + association;
- reduced-motion support;
- no unexpected focus moves on HTMX updates;
- concise live-region result announcements;
- accessible chart alternative.

## 9. Performance budgets

Initial goals, subject to measurement:

- server-rendered critical path;
- no web JS framework bundle;
- minimal HTMX payload;
- CSS purge/build optimized;
- no blocking cultural-media dependency;
- avoid N+1 queries;
- bounded provider latency with cache fallback.

Performance work must be evidence-driven.

## 10. Reliability states

Every network-derived feature must explicitly model:

```text
idle
loading
success
stale-success
empty
retryable-error
non-retryable-error
```

Do not collapse “stale but usable” into generic error.

## 11. Deployment checks

Before production:

- `manage.py check --deploy`;
- migrations clean and reproducible;
- static build deterministic;
- secrets absent from repository;
- health endpoint verifies app and database readiness;
- rollback procedure documented;
- provider outage does not break static/cultural pages.

## 12. Definition of done

A feature is not done until:

- acceptance criteria pass;
- domain behaviour is tested;
- error/recovery state exists;
- accessibility is reviewed;
- docs/ADR are updated when needed;
- no new secret or unsourced trust-sensitive datum is introduced.


## 13. Historical conversion quality strategy

Historical FX introduces trust-sensitive temporal behaviour that requires dedicated tests.

Minimum unit/contract coverage:

- exact historical date;
- weekend/holiday missing observation;
- requested vs effective date preservation;
- out-of-coverage date;
- archived currency;
- unsupported pair/date;
- observation granularity;
- Decimal correctness;
- Then & now directional comparison;
- provider correction/cache invalidation path where applicable.

Browser/E2E coverage:

- switch Latest available → Historical date;
- choose date and convert;
- clearly identify effective observation date;
- archived currency discoverability;
- country/date historical-currency suggestion;
- historical deep-link reload;
- story unavailable while conversion remains successful.

## 14. Story quality and provenance tests

Story composition should be testable as deterministic output over structured facts.

Verify:

- no chapter without required source metadata;
- temporal filtering excludes irrelevant future/past facts;
- missing optional facts shorten story rather than create filler;
- no story path modifies numeric conversion;
- archived currencies do not get fabricated current quote chapters;
- causal phrasing is never generated merely from date proximity;
- story order follows product relevance;
- source links/labels remain available to presentation.

## 15. Temporal accessibility

Historical date controls and stories must preserve WCAG 2.2 AA baseline.

Test:

- date selection by keyboard;
- understandable label for historical/latest mode;
- requested/effective dates announced/read in logical order;
- timeline milestones available as semantic text/list;
- historical chart has text/table alternative;
- story loading does not announce the entire narrative through a live region;
- no colour-only difference between historical/current/cached states.

## 16. Historical trust regression rule

Any bug that can cause one of the following is severity-high:

- wrong pair shown with a valid-looking historical result;
- wrong effective date;
- current rate labelled historical;
- archived currency given fabricated current quote;
- current price context presented as historical purchasing power;
- story claim shown without provenance;
- user-requested date silently changed.

These failures are more serious than cosmetic rendering defects because they undermine product trust.
